# 且慢 · 一封信与财富记忆

把已经核实的记录写成一个人愿意保存的文字。让客户看见自己重视的生活，理解钱的变化，并能亲自补充、删改自己的故事。

## 读取资源

- 首次执行、用户问“参考谁”或需要更新语料时，读 [references/source-atlas.md](references/source-atlas.md)。
- 每次写作前读 [references/editorial-method.md](references/editorial-method.md)。
- 接收客户数据、批量运行或结构化交付时，读 [references/data-contract.md](references/data-contract.md)。
- 写作前确定三种成品的区别，读 [references/output-contract.md](references/output-contract.md)。
- 需要示范或比较客群路由时，读 [references/original-examples.md](references/original-examples.md)。
- 需要合法、可复现的演示输入时，使用 [assets/demo-customer.json](assets/demo-customer.json)。始终保留“虚构示例”标记。

## 核心选择

提炼通用方法，使用原创且慢服务语气。不要声称模拟真人本人、得到作者授权、由真人写作或真人已审阅。

| 来源 | 可借鉴的方法 | 应用 |
| --- | --- | --- |
| 林杰才的周年来信 | 用可核验的共同经历展开意义；承认服务尚有不足 | 私人来信的价值结构 |
| Iris 的人物访谈 | 先问生活，再问钱；保留人物自己的说法和有辨识度的细节 | 财富记忆、人生目标 |
| ETF拯救世界的公开文字 | 对困难直说，解释行为与责任 | 波动期来信 |
| 郭志强的家庭账户专栏 | 把资金放回用途、时间与持续复核 | 财富档案 |
| 且慢团队的四笔钱内容 | 把复杂的财富信息组织成可理解的底稿 | 档案与下一步 |
| 简七、孟岩的历史合作或历史陪伴内容 | 用普通语言解释选择，容许不知道，保留自我反思 | 语言审读与历史参照 |

区分公开作者、团队署名、历史人员与当下任职。只按证据标注，未经核实不把公开笔名映射为员工真实姓名，不把机构账号全部文章归给负责人。

## 执行流程

### 1. 确认本次交付

默认同时生成：
1. **一封信**：中文约 450–700 字；资料不足时主动缩短。
2. **财富档案**：一页摘要，必要时展开底稿。
3. **财富记忆**：1–3 个有依据的时刻；没有可用事件时保留空白。

用户指定一种成品时仅交付该种。未要求发送时只生成草稿；不触达客户、不启动提醒、不替用户交易。

### 2. 先建事实底稿

把资料区分为：
- 系统已核验事实：账户、对账完成的损益、交易或服务完成事件。
- 本人已确认事实：生活目标、资金用途、原话、已发生的生活事件。
- 有条件的计算或解释：保留输入、公式、范围及所需条件。
- 未知、冲突、过期、未经确认：不当成个人事实写入正文。

给可用事实分配 `F01` 等证据编号；为客户材料保留客户标识、授权用途、数据范围和快照时间。公开语料只提供写作方法，绝不提供客户人生事实。

运行 `python3 scripts/validate_packet.py assets/demo-customer.json` 可检查输入格式与简化资金勾稽。真实账务以源系统口径为准；脚本不会计算收益率或替代账务对账。

### 3. 先选一个值得写的事实

优先选择：
1. 本人说过在意的生活目标；
2. 已确认用途且已经完成的一次资金取用；
3. 本人确认的计划改变；
4. 一段有可靠口径的资产变化；
5. 一次已经完成、且与客户有关的服务。

按“与本人相关、可核验、值得记住、本人愿意保留”判断，不按交易金额、资产等级或平台获利排序。不要为了凑齐三段制造事件。

### 4. 选择写作路线

多种状态可以重叠；先处理近期用款和明确异议，再处理盈亏。

| 状态 | 着力点 | 避免 |
| --- | --- | --- |
| 亏损 | 先说真实损失；再写已确认生活与可控制的下一步 | 把损失称为礼物、默认劝持有或补仓 |
| 盈利 | 清楚呈现来源与口径；问目标是否改变 | 将盈利归因于能力、暗示未来可复制 |
| 近期用款 | 写已知金额、日期、可用性与待核对项 | 承诺到账、要求为长期回报放弃生活需要 |
| 无资产或新用户 | 给可编辑的起步档案与一个轻量问题 | 编造第一笔投资、财富规模和家庭角色 |
| 低活跃 | 展示已知变化，邀请确认旧目标 | 把不登录解释成从容、自律或认可 |
| 已赎回 | 尊重选择、回顾已完成记录；当前外部状态未知 | 认定赎回错误、制造亏欠感或召回压力 |
| 资料不足 | 交付已知部分，用一个具体问题留下空白 | 以空泛赞美假装了解 |

### 5. 分别写三种成品

**信：** 用一个具体事实开头 → 如实说明今年钱的变化 → 联系本人确认的生活或目标 → 给一个可选的下一步 → 简短结束。保留呼吸感，让数据服务于叙事。不要让每封信都使用同一句开场。

**档案：** 写明时间与范围；区分投入、取用、损益及期末资产；资金用途与资产类别分开展示；保留已确认目标和未知项；提供至多三条“事实—解释—条件—选择”的发现。

**记忆：** 对每个时刻写“日期或时间精度＋发生的事＋本人确认的意义（如有）＋可编辑留白”。使用原话需来自该客户且适用于本次用途；不凭交易记录虚构当时的情绪。

三种成品共用同一事实底稿，但分别承担被看见、看清楚、记得住的作用，不要重复粘贴同一段内容。

### 6. 审读与修订

逐项检查：
- 每个人名、数字、时间、目标、生活事件、心理描述能否回到证据。
- 年度未结束时是否清楚标为阶段版；不能在 11 月宣布全年结果。
- “去年/今年”是否与客户所在地、报告期间一致。
- 账户增长是否误当成投资收益；净转入是否误当成储蓄。
- 低活跃、亏损、赎回、年龄和性别是否被写成品格判断。
- 模型解释是否被写成客户确认的意义。
- 是否复用了别人的生活故事、私人原话或匿名笔名的真实身份推断。
- 是否出现保证盈利、默认持有、羞辱退出、促成交易的情绪操纵。
- 去掉客户名字后，是否仍可以发给任何人；若是，回到具体事实重写。
- 客户读完是否有一种可以带走的价值：一个准确的发现、一个记忆、一个被保留的问题或一个自己的安排。

把“温暖”落实为准确、尊重和可修改。保留必要风险和范围说明，但不要用长篇制度措辞淹没信件。

### 7. 交付与批量运行

客户版只呈现正文、范围和必要说明。内部版追加事实清单、证据编号、缺失信息、编辑评分与待处理项。

按 [references/output-contract.md](references/output-contract.md) 输出结构化版本时，每个事实性段落标注 `evidence_ids`。发布前运行 `scripts/validate_bundle.py`；它只能做格式、证据归属和明显禁语检查，仍须进行语义和专业审读。

批量运行每次只向模型传入一位客户的必要资料；在客户标识、证据归属或对账上发生冲突时停止该客户的个人化生成，保留基础版和内部待处理项。不要把一位客户的材料作为下一位客户的示例上下文。

未接入真实客户数据时交付明确标记的虚构样张、可运行的输入和模板；不宣称已为所有客户生成或交付。
